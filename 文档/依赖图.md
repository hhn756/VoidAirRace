# 依赖图

为「事件优先级控制初始化改成 DI」（TODO 第 4 条）盘点的模块级依赖图

边 = 引用方包内有文件 `import` 被引用方包的类（基于全量 import 扫描，2026-09-30）

## 术语表

| 术语    | 含义                                               |
| ----- | ------------------------------------------------ |
| 模块    | 顶层包（如 `infrastructure.config`、`core.match`）      |
| 依赖边   | A -> B 表示 A 包引用了 B 包的类，A 依赖 B                    |
| 启动初始化 | `PluginEnableEvent` 处理器内的 `load()` / `init()` 调用 |
| 运行时依赖 | 事件处理器（非启用事件）、比赛运行期间才触发的调用                        |
| 组合根   | 集中按依赖顺序构造、初始化模块的位置                               |
| 巧合顺序  | 现有优先级恰好正确但无依赖关系支撑的顺序                             |

## 三、启动初始化链现状

`onEnable` → 注册监听器 → 发布 `PluginEnableEvent`，各模块按 `EventPriority` 接管：

| 优先级    | 模块                  | 执行内容                                                                           |
|--------|---------------------|--------------------------------------------------------------------------------|
| LOWEST | config              | `Config.load()`                                                                |
| LOWEST | registry            | `Registry.load()`                                                              |
| LOWEST | usrpackage          | `PackageManager.load()`（发布 `UsrPackageLoadEvent`）                              |
| LOWEST | team                | `TeamRoster.load()`                                                            |
| LOWEST | schedulingutil      | `SchedulingUtil.init(主类)`                                                      |
| LOWEST | blockfinder         | `BlockFinder.plugin = 主类`                                                      |
| LOW    | map                 | `Registry.createCategory` + `MapInitializer.load()` + `initAllMapsAsync()`     |
| LOW    | playerstatemanager  | `StateRegistrar` / `PlayerInitializer` / `PlayerStateManager.load()` + 在线玩家初始化 |
| NORMAL | match               | `ComponentRegistrar.load()` + `MatchCoordinator.load()` + `checkMatchAbort()`  |
| NORMAL | arena               | `ArenaManager.load()`                                                          |
| HIGH   | audiovisualservices | **仅运行时**（防音效被传送截断），与初始化无关                                                      |

另有 `Bootstrap`（Paper 引导阶段，先于 `onEnable`）通过 `BootstrapStage` SPI 引导（加载逻辑在 `Modules#bootstrapAll`）：命令注册（`MatchCommand`、`GameMapCommand`、`PlayerManagerCommand`）、数据包注册（`DataPackRegistrar`）。

## 四、顺序约束分析

**被依赖关系要求的顺序（必需）：**

1. config、registry 早于 map / playerstatemanager / match / arena（后者初始化直接调用前者）
2. registry 早于 map（`createCategory`）、playerstatemanager（`StateRegistrar` 注册类别）、match（`ComponentRegistrar` 注册组件）
3. schedulingutil、blockfinder 早于 map（`MapInitializer.initAllMapsAsync`、grassland 地图初始化使用）
4. 全部晚于 `onEnable` 开始（需要主类实例）

**巧合/无约束的顺序：**

- LOWEST 层六个模块互相之间**零依赖**（已核对全部 import），相对顺序纯靠类扫描顺序
- usrpackage、team 在 LOWEST 层没有向下依赖证据（`PackageManager` 只依赖 constants/event/exception/result；`TeamRoster` 只依赖 TranslateKeys）
- 隐患：`PackageManager.load()` 发布 `UsrPackageLoadEvent`，监听者若依赖 registry/config，则 usrpackage 需晚于它们——当前同为 LOWEST，靠扫描顺序碰巧成立

## 五、包级循环依赖（DI 改造前置障碍）

1. **event ↔ core.match**：事件类携带 `Match`、`DataKey`、`CustomData`、`MatchComp`；`Match` 发布 `MatchStartedEvent`/`MatchOverEvent`。类级互引（事件承载业务类型）。
2. **constants ↔ core.\***：`Categories.java:L3-L7` 引用 `MapEntry`、`CompEntry`、`MatchComp`、`RuleEntry`、`StateSystemEntry`，而 core 各模块反向引用 `Categories`。常量包依赖业务包，方向反常——与 TODO 第 2 条（注册项类别 `CategoryId` 化）相关，可一并解决。
3. 无环确认：core.map → core.matchrule 单向；core.playerstatemanager → core.match 单向；core.match 不反向依赖 map/playerstatemanager。

## 六、拓扑分层（DI 改造的组装顺序）

```
第 0 层  result、exception、constants(除 Categories)、infrastructure.util.*
第 1 层  infrastructure.config、infrastructure.registry
第 2 层  core.team、core.addons.usrpackage
第 3 层  core.match（不依赖其他 core 模块）
第 4 层  core.map、core.matchrule、core.playerstatemanager、event(事件类)
第 5 层  service.arena、playerinteraction.audiovisualservices、playerinteraction.command
```

改造方向：把「注解优先级数字」换成「组合根里的显式构造顺序」。bootstrap 阶段已有 `BootstrapStage` SPI 先例，enable 阶段可建立同构机制（如 `EnableModule`）或直接在组合根按上表顺序显式调用各模块 `load()`，并删除各模块 `EventListener` 中仅用于排序的 `onPluginEnable` 处理器与排序用 `EventPriority`。
